## 官方协议与当前实证

官方来源：<https://learn.chatgpt.com/docs/app-server>，本次实际读取。
`thread/list` 是历史索引，`thread/loaded/list` 是内存实例索引；读取不等于订阅。
订阅通过 `thread/resume` 恢复，退订不保证立即卸载。不能用历史可读性推断当前 writer
归属，也不能把 `thread/delete` 或 archive 当作连接清理。30 秒快照和 16 MiB 输出缓冲
阈值是 Bridge 的恢复策略，不是官方协议要求。

本机日志 `20260908T011339/window1/exthost/openai.chatgpt/Codex.log:189` 起记录
`thread/resume` 的 `already has an active writer`。只读进程检查发现旧 Shim `18292`
已死亡，旧 app-server `18352` 仍打开对应 rollout 和 writer lock；通过其受管通道读取
loaded 索引和 thread 状态，确认目标线程仍在内存且为 idle。未终止用户该进程。
这证明占用未释放，不证明历史丢失。

当前官方 Webview `app-initial-c518b37afd45.js` 的通知处理器在 `thread/started` 中
调用 `upsertConversationFromThread` 和 `broadcastConversationSnapshot`。候选使用这一
既有接收路径传递服务端完整快照，不补丁修改官方资产；真实渲染恢复仍待 M11 验收。

## 实现边界

- 注册表区分历史、loaded 集合和 UI 当前线程；外部读取不抢占当前线程。
- 已死亡 Shim 的匹配 app-server 通过进程启动时间、可执行路径、受管凭据与互斥 claim
  接管；新记录落盘且连接成功后才删除旧记录。PID 复用、活跃所有者、未知状态不接管。
- 重新连接后分页发现后台线程，只为当前工作区运行线程恢复订阅；定时服务端快照和
  完成态补齐不重发用户输入，不调用 `turn/start`。WS 心跳和输出积压触发连接回收。
- 断开后保留 Linux 本地 app-server；接管期过后，Controller 每分钟检查可验证空闲实例。
  Controller 全部退出时维护暂停，下次激活继续。历史保留与进程回收互不等同。
- 多个不同 detached app-server 同属一个工作区时明确报歧义，不随便挑一个或强杀。
- Remote SSH 保活接管尚未开启，避免把旧动态工具/MCP transport 当成重载后仍可用；
  Windows 的后台接管仍待实现和验收。既有 Remote SSH 执行协议未变。
