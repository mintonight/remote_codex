## 实现与协议依据

- 服务按规范根、CODEX_HOME 与启动参数寻址，版本、窗口 PID、thread ID 不参与身份；
  `flock --nonblock --no-fork` 是 Linux 实际能力要求，不按组件版本拒绝连接。
- daemon 独立持有 native app-server 与恢复订阅，窗口只转发 stdio。客户端退出不发
  turn/interrupt；请求结果未知时不重试写操作；慢连接超过缓冲限额只断开该客户端。
- 每个 thread 的执行与排队仍使用官方引擎。原样透传 thread/queue/*、turn/start、
  turn/steer、turn/interrupt，不把队列 ACK 伪造为 TurnStartResponse。并未把
  turn/start 改造成 Bridge 自建 FIFO；客户端需要明确使用官方队列。
- 审批以服务唯一 ID 分发，首次回答送回原 native 连接；断开后的待审批可被新客户端接回。
- 服务只在索引确认无 loaded thread、无客户端/孤立执行连接持续 30 分钟时自动退出。
  显式 bridge/service/stop 对其他客户端、loaded thread、未知状态采取保守拒绝。
- 服务崩溃可从私有 journal 接回原 native PID；不扫描接管未受管 Codex App，不按进程名
  清理用户后台。旧窗口还活跃时拒绝并行迁移，需要用户重载旧窗口。
- [官方 App Server 协议](https://learn.chatgpt.com/docs/app-server#protocol) 和
  [线程生命周期](https://learn.chatgpt.com/docs/app-server#threads) 是协议依据。
  当前安装二进制的 experimental JSON schema 实测含 thread/queue/add、list、update、
  delete、reorder、start；以消息结构/实际操作判断能力，不固定该二进制版本。

## 遗留风险与结论

- 本次没有修复或改写官方 Webview/Workbench。详情展开触发的 renderer 灰屏仍是独立
  问题，不能从后台生命周期成功推断灰屏已解决。
- Remote SSH 的执行通道重绑定、Windows 服务实现、服务升级排空仍待实现/补测；
  本地独立服务只接纳当前唯一文件工作区，不改造远端 workspace URI。
- 不接管仍由旧窗口使用的后台，需要用户手动重载。已发现的配置域不匹配不会被迁移。
- 最终结论：Linux 独立服务候选；非正式发布。遵守真实 VS Code/Remote SSH 验收后再
  提交集成修复的门禁，本次不提交、不推送。
